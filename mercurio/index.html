Mercurio a local, multi-project software factory

The intelligence is in the harness, not the model.

Mercurio is one service on the owner's machine. It reads each project's GitHub Project, runs every queued card through a fixed chain of small Claude Code sessions, checks each one with a gate the service runs itself, and shares the machine among every project.

Semi-autonomous by design. The factory proposes, the owner approves. Only the owner queues work, and every change to the factory or its memory waits for the owner.

01 The problem

Agents made writing code cheap. They did not make integrating, reviewing or running it cheap.

The constraint did not disappear. It moved downstream, to human review and the merge queue. A factory has to be designed around that fact.

“The constraint didn't disappear. It moved downstream, to the narrowest pipe in the system.”
Tian Pan, The Merge Queue Is the New Bottleneck

lines of code on GitHub, while releases grew 30%. NBER WP 35275, via Sonar

at most, through a 30-minute merge-group CI, if nothing fails. Tian Pan

AI tools raise the volume of pull requests but do not change deployment frequency or lead time Augment Code. Inference Speeding up only the parallel part, writing code, runs into the serial part: review, merge and deployment Amdahl's law, Splunk. The source itself warns that Amdahl does not hold when the load grows, which is exactly what agents do, so the frame orients rather than calculates.

Why one long-running agent fails

Most products that call themselves AI agents are “mostly deterministic code, with LLM steps sprinkled in at just the right points” 12-factor-agents. Agents get lost as the context grows: “anything more than 10-20 turns becomes a big mess that the LLM can't recover from”. The recommendation is agents of “3-10, maybe 20 steps max” inside a deterministic DAG.

Anderson reaches the same place from operations: “AI agent CLIs are reasoning engines, not process managers” Anderson, arXiv 2604.09388. And from the review process: “A model that guesses the next step guesses differently tomorrow” gentle-ai.

The evidence is mixed, and Mercurio's design takes that seriously

The best-documented case went from 16 to 81 merged PRs a day over 100 days with one maintainer Anderson. A controlled experiment measured developers 19% slower with AI while they believed they were faster METR, via ai.engineer, and across 8.1 million PRs, AI-assisted ones merged within 30 days 32.7% of the time against 84.4% for manual ones LinearB, via Enpitech. Inference The reading most consistent with every source: the gain exists where gates are strong, work is bounded and tests are deterministic, and it is absent or negative where they are not.

02 The principles

Four ideas, repeated by independent sources, decide the shape of the factory.

They come from a synthesis of 41 sources read for Mercurio in November 2026. Each card shows the claim, its source, and the decision in Mercurio that follows from it.

Principle 1

Intelligence lives in the harness

The intelligence of an AI-driven development system resides not in the AI model itself, but in the infrastructure of instructions, tests, metrics, and feedback loops that surround it. Anderson, arXiv 2604.09388

The same model produced 72.6% functional and 29.0% secure code in one harness, and 59.8% and 19.0% in another Endor Labs.

In Mercurio. The harness is mounted per session, chosen by project, factory and phase. The service decides every transition; a session's account of its own work is not evidence, the gate runs on the artifact.

Principle 2

Gates must grow faster than generation

Agents optimize to pass the gates, and weak gates turn high volume into unusable output. hackers&wizards

If the gates do not catch what the human reviewer caught, “the factory ships what the reviewer used to stop” Weave.

In Mercurio. Agents never edit the guards that judge them. Verification runs the QA branch's copy of the checks, so a branch cannot change the checks it is judged by, and a retrospective that touches a gate is refused.

Principle 3

Autonomy in proportion to what can be verified

Only the autonomy you can verify. Sonar, quoting Osmani (translated)

A loop runs unsupervised only if its verification is cheap, frequent and hard to fool. The more irreversible the action, the stronger the human gate Roest.

In Mercurio. Only documentation and frontend paths may skip the person, never an always-human path. Every fast-lane merge is sampled by the owner until 20 samples exist; the lane stays as wide only while samples find nothing the gates missed.

Principle 4

Maturity is feedback loops, not autonomy

Autonomy is an output of maturity, not a definition of it. Anderson

Levels are defined by the topology of feedback loops, and none can be skipped. Each is unlocked by another feedback mechanism.

In Mercurio. Every station run is appended to an event log that nothing edits. Before a prompt, a profile or a model changes, recorded cards are run again and their gate results compared.

03 The factory

A chain of stations with gates, and a routed exit.

Four fixed factories, define, draw, code and test, are the same for every project. Inside them a card runs six stations. Each is a separate Claude Code session with one contract: input artifacts, output artifacts, a gate the service runs, and a named authority. Select a station to see what it does and what happens when it fails.

When a gate fails

The state of a card is an event log in SQLite that nothing edits. Pausing, resuming after a restart and running a station again are the same operation: start from an event.

1. Retry clean

The card returns to the same station with the reason. The retry is a new session that gets the artifacts and the failure in short form, never the transcript of the attempt before.

2. Block

After the station's retries the card is blocked, with the reason and the way out written on it.

3. Owner requeues

Moving a Blocked issue back to Queue runs that station again on a fresh attempt budget. The CLI can widen a task's edit surface or hand the card a missing file first.

4. Back off

A run that throws waits before the next try: 1 minute, doubling up to 30.

Tasks are cut to the model that writes them

The define session cuts tasks to the profile of the model chosen for the card. The smaller the model, the more of the decision arrives already made in the task. A task that fails twice on one profile is queued again on the next one up.

04 Where the human enters

The owner is stopped only for a decision. Everything the factory does on its own is checked by something that is not the model.

Each stop is one structured request with its options, not free text. Slack shows it; the answer is appended to the card's log and the service resumes the station the request names. Only the owner's Slack answers are recorded.

The design rule behind the stops

Mercurio's goal is a factory that runs a card with as few owner stops as it safely can (ADR 0004). That is why functional analysis, technical analysis and slicing became one define session: three sessions could each ask the owner, and the owner approved a spec on every card. Now the owner approves a definition only when its plan is high risk.

06 How it improves itself

Two loops, kept apart. Neither applies anything without the owner.

A retrospective changes how the factory works. A dreaming pass changes what the factory remembers. They run on a schedule outside any card, read only recorded runs, and never touch the gates the factory is judged by.

Rules that keep the loops honest

The retrospective works from records, not from its own opinion of the code. It looks for a check that fails the same way at one station, tasks climbing to a larger profile, escalations of one kind, and what the fast-lane sample found. It sees only what the event log records, so a failure the log does not capture is never proposed for a fix.

The dreaming pass treats a transcript as data to draw facts from, never instructions. A fact carries its date and the run it came from. A credential is named, never copied. The service snapshots memory before the pass, checks afterwards that every transcript in the window was read, and stops the pass at a cost cap.

Stations will read memory live through a read-only proxy that pins the project in code and refuses an observation from another project (ADR 0005). The same fence is what later lets learning cross projects without leaking memory between them.

What has run so far

PassReal runsLands as
Retrospective1, on a test store; its PR was mergedPR against QA with replay comparison

The production store holds 287 recorded runs, all with transcripts. Neither pass has run on it yet (roadmap, 2026-11-15).

Where the loop does not close yet

  1. Approved memory reaches no station. A plain mount does not fence a project, so no station reads Engram until the fenced proxy lands.
  2. Nothing measures a dream. There is no comparison before and after a memory change.
  3. The measurement set is stale. Its runs are all of stations the one define session replaced.
  4. Coding cannot be replayed. Coding prompt and model changes cannot be measured yet.
  5. The dream window starves. A 1 MB bound let the only real pass read 3 of 40 runs.
  6. Undo is manual. The applied steps are listed, but no command runs them back.
  7. Both passes run only on demand. One pass of each was too little to pick a frequency.

07 Sharing the machine

Many projects, one machine, explicit limits.

Mercurio runs as a user systemd service, so the caps hold whenever the machine is on. Each project brings its own Claude account and credentials; Mercurio measures each and holds back its own sessions.

Updating without stopping work in the middle

Every project runs the latest Mercurio, so a new version applies only when nothing is running. When Mercurio's own checkout moves to a new commit, the service drains: it starts no new card, lets the running ones finish, waits until no Claude session of any process runs, and exits so the unit restarts it on the new commit.

Two cards run at once only when their edit surfaces do not overlap.

08 Review

A mechanical layer first, then four lenses. The verifier is never the author.

Verification runs on the frozen commit. The verifier for the lenses is the strongest model that did not write any of the card's tasks. When no model is free, the card goes to a person; it is never blocked for that.

Layer 1, always first

Mechanical

  • Tests on base and on the candidate
  • Types, lint, secret and dependency scans
  • Accessibility and declared UI states, when the change touches UI

No lens starts on a candidate that fails it.

Layer 2, read-only, not the author model

Lenses

code requiredAlways runs.
security requiredRuns when the change touches an always-human path.
ui optionalRuns when the plan says UI and the card has its design.
ux optionalSame condition as ui.

A project may leave out ui or ux. It can never leave out code or security.

What blocks

Only the candidate's severe findings

A finding blocks only when all three hold:

  1. it is a blocker
  2. the candidate caused it
  3. its file is in the diff

One bounded correction round follows. If it does not close the finding, the change goes to a person, with every finding in the pull request.

09 Roadmap

Grow in steps. A phase starts only when the one before meets its exit criteria.

The implementation plan's main line and side track are done: the event log, the stations, routing, lenses, cost per card, both self-improvement passes, Slack, the GitHub board, the web page, resource arbitration and the design station. Each phase below states what it proves, not only what it builds.

Phase 1 · now

The self-improvement loop works on production

  • Refresh the measurement set from production runs
  • Run the retrospective and the dreaming pass on the production store
  • Let the dream window cover the backlog
  • Stations read memory live through the fenced proxy
  • Measure a dream: replay with and without the approved memory
  • Undo an applied dreaming pass with one command
  • Three cycles of each, then pick a frequency and schedule both

ExitThree cycles of each pass on production, each one decided and measured, running on a schedule.

Phase 2

Pick the next work

Candidates the repository already points at, each needing evidence and a cost estimate before it is queued:

  • Coding replay, the largest gap in the retro loop
  • QA to production promotion, by hand today
  • Notifiers, terminal backends and board adapters beyond the first
  • A second project on the factory
  • Model comparison beyond retro replays

ExitA backlog ranked by expected value over cost, each item queued as a card with its evidence.

Phase 3

Scale out

  • Onboard a second, external project end to end
  • Finish the caps for several projects: disk, ports and database names
  • Let the self-improvement loop learn across projects without leaking memory between them

ExitTwo projects run in parallel for a week with no manual intervention beyond queueing and approvals.

Still out of scope: running in the cloud, triggering work from anywhere, and a knowledge graph, until a phase above gives a reason to reopen them.
